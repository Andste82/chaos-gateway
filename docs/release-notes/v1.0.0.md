# Chaos Gateway 1.0.0

The first release: a programmable network test gateway for devices under test. A Linux machine between a test network and the
upstream network that routes, NATs, serves DHCP and DNS, and on top impairs, breaks, intercepts and records the traffic of
individual devices, from a web app, a REST API and a command line client. It runs as containers on Ubuntu 24.04 and 26.04 LTS, on
x86-64 and ARM64 (with the qualifications [below](https://github.com/Andste82/chaos-gateway/blob/v1.0.0/docs/release-notes/v1.0.0.md#not-validated-on-arm64-until-the-hardware-lab-has-run)).

Documents: [user guide](https://github.com/Andste82/chaos-gateway/blob/v1.0.0/docs/user-guide.md), [API guide](https://github.com/Andste82/chaos-gateway/blob/v1.0.0/docs/api-guide.md), [scenario cookbook](https://github.com/Andste82/chaos-gateway/blob/v1.0.0/docs/cookbook.md),
[installation](https://github.com/Andste82/chaos-gateway/blob/v1.0.0/docs/install.md), [troubleshooting](https://github.com/Andste82/chaos-gateway/blob/v1.0.0/docs/troubleshooting.md), [recovery instructions](https://github.com/Andste82/chaos-gateway/blob/v1.0.0/docs/recovery.md).

## What is in it

- **Gateway**: routed test networks with NAT, DHCP (Kea) and a DNS proxy; the access matrix between networks; WireGuard hubs for
  clients and point-to-point links, with static and dynamic routing (BIRD: BGP, OSPF, Babel) and import protection; port forwarding to
  devices; probes (virtual clients) and their management in the web app and with `chaosctl`.
- **Faults**: latency, jitter, loss (also bursty), rate and queue limits, reordering, duplication, corruption, blackout, flapping, MTU
  and path MTU faults, tunnel faults, per device, group, network or globally, with a precedence you can ask about (`explain`);
  profiles, built in and your own; access rules (allow, drop, reject, TCP reset, cutting existing connections).
- **Application layer**: DNS faults, TLS certificate and handshake cases with a test CA, DHCP actions (short lease, deleted lease,
  new address, options, silence).
- **Automation**: overlays with TTL and lease, scenarios with checks and zero-hit warnings, runs with JSON and JUnit reports, the event
  stream, Prometheus metrics, `chaosctl` (including `with`, which runs a command under a fault and cleans up), generated Python and
  TypeScript clients with example suites.
- **Evidence**: packet captures (pcapng, ring buffer, quota, attached to runs), per-rule and per-fault counters, a flow view,
  diagnostics from the gateway or from a probe, the audit log.
- **Operations**: configuration in immutable revisions with preview, commit-confirm and rollback; the last known good revision and a
  safe mode when a configuration cannot be applied; a stop that removes everything the gateway made in the kernel, and `teardown`; one
  multi-arch image, one `compose.yaml`, a host setup and an update script that waits for running tests; HTTPS with a certificate you
  can replace; the hardening of the containers.
- **Web app**: Overview, Devices, Flows, Networks (with WireGuard, routing, port forwards, DHCP), Access rules, Faults, Profiles,
  Scenarios, Captures, Diagnostics, and the first-start wizard.

Optional parts that are built and in the image: the interception proxy (the case `intercept`: decrypt the TLS of a device that trusts the
gateway's CA and change the HTTP exchanges; mitmproxy in its own container, `compose.tlsproxy.yaml`). Its screen (**Interception**) is in
the web app but is **not part of the scope of this release** (it ships after V1): the API and `chaosctl` are the supported way to use it.

Not in this release: VLANs, IPv6 (IPv6 forwarding is blocked so faults cannot be bypassed over it), the gateway's own NTP server and time
faults, faults on connections that reach a device through a port forward, a three-way merge of concurrent revisions, rule captures via
NFLOG and live streaming to Wireshark, traceroute and iperf3 diagnostics, continuous drift detection, a native `.deb` package.

## Not validated on ARM64 until the hardware lab has run

The image is built for ARM64, the Go unit tests run as ARM64 binaries under emulation (`qemu-user`), the image's smoke test starts the
ARM64 binaries and tools, and a weekly job boots an emulated ARM64 Ubuntu machine and runs the end-to-end smoke test of the whole stack
on it. **No Raspberry Pi or other ARM64 hardware has been available**, so the hardware validation (plan H1) has not run. Until it has:

- **The Raspberry Pi targets are unvalidated.** The performance targets for a Raspberry Pi 4/5 (forwarded throughput with faults of at
  least 100 Mbit/s, 50 devices, 50 simultaneous faults, an overlay apply of at most 200 ms, 100 overlay writes in 2 s, capture without
  loss at 50 Mbit/s, DNS answers for hostname sets within 20 ms, and a throughput of at least 20 Mbit/s through the TLS proxy) are goals
  that nobody has measured. The same holds for the
  default class limit on ARM64 (200 classes per interface), the loss and delay accuracy on a real NIC with the offloads switched off,
  and the limit of 1000 access rules.
- **The timing of scenarios on ARM64.** The promise that a step is handed to the engine within 100 ms of its schedule is measured on
  x86-64 only. The tolerance for ARM64 is set when hardware has been measured; on a small machine an apply takes longer and the
  report shows both moments of every step.
- **The interception proxy is not validated on ARM64.** mitmproxy's throughput (the target of section 3.10 for it, at least 20 Mbit/s on a Raspberry Pi, is unmeasured), its memory with large bodies buffered (a body is
  buffered to change it) and its CPU per connection on a Raspberry Pi are unknown; the container has no memory limit because none was
  measured to be safe. Use the interception for test setups with a few devices, and do not rely on it on ARM64 hardware until H1 has
  measured it.
- The namespace testbed (level 1) and with it the accuracy tests of the faults run on x86-64 kernels in CI only; the ARM64 image is
  covered by the emulated smoke tests above.

x86-64 is measured: the accuracy of the faults (hosted runners with KVM) and the packet plane.

## What was not reviewed from outside

The executor, the one privileged container, accepts a closed list of typed operations over a Unix socket. It has a written threat
model, six fuzz targets (6 minutes in every CI run, 45 minutes each nightly) and a table of mitigations with the test that holds each
(`docs/development.md`, "Security hardening (M29)"). **It has not been reviewed from outside the project.** The external review is not part of V1;
it follows with the deferred items after V1 (M38), and this release goes out with the self-review and the fuzz runs. Read the container table before you put the gateway where
untrusted code can reach the API.

Also accepted for this release: the `kea` container runs without `no-new-privileges` (read-only root, five capabilities; the tests keep the
exception from growing); the container of the interception proxy has no memory limit.

## Behavior you should know

- **A stop removes the test networks.** Stopping the gateway (or updating it) removes everything it made in the kernel; devices lose
  their gateway and DHCP until the new start has rebuilt the networks from the last confirmed revision (seconds to a minute). Leases are
  kept.
- **Safe mode** (when no revision can be applied) keeps the management interface only. A WireGuard network of the role `management` is
  down in safe mode, so the way in is the management interface ([recovery](https://github.com/Andste82/chaos-gateway/blob/v1.0.0/docs/recovery.md#safe-mode)).
- **A fallback to a revision from before a WireGuard key rotation** cannot be applied (the rotation retired the old key) and ends in
  safe mode; the way out is a new revision.
- **Overlays do not survive a restart**; tests start from a clean baseline.
- **Checks read the connection table**, so a packet the gateway drops is not seen by `traffic_seen` / `traffic_not_seen`
  ([user guide](https://github.com/Andste82/chaos-gateway/blob/v1.0.0/docs/user-guide.md#scenarios-and-runs)).
- **The web app has no screen for API tokens yet**; make them with the API ([API guide](https://github.com/Andste82/chaos-gateway/blob/v1.0.0/docs/api-guide.md#tokens-and-scopes)).

## Upgrading and installing

Install as in [install.md](https://github.com/Andste82/chaos-gateway/blob/v1.0.0/docs/install.md): `docker pull ghcr.io/andste82/chaos-gateway:1.0.0`, take the host setup out of the image and run
it once, start `compose.yaml`, finish the setup in the browser. The files of the deployment (`compose.yaml`, `host-setup.sh`,
`update.sh`, `env.example`, `SHA256SUMS`) are attached to this release for a host that has no Docker yet. Later versions are installed
with `update.sh`, which refuses a configuration that needs a newer version than the image, waits for running tests and checks the new
image before it stops anything.

## Verified documentation

Every example in the user documents that can run does run in CI (`make test-docs`, the job `docs`): the shell examples against a
gateway on the simulated kernel with the real engine, their printed output against what they print, and every document and scenario in
them against the schemas of `api/openapi.yaml`. The examples show the shapes of requests and answers as the API has them.
